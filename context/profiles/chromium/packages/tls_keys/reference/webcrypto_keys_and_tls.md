# WebCrypto keys and TLS client authentication

WebCrypto-generated keys never reach the platform TLS stack — no browser
exposes a `CryptoKey` to a TLS `CertificateRequest`, which bounds what any
in-browser enrollment or CSR flow can promise on every platform and browser.

A key generated by `SubtleCrypto.generateKey` lives in the browser's
own key store and is never reachable by the platform TLS stack. **No
browser exposes a WebCrypto `CryptoKey` to a TLS
`CertificateRequest`** — on any OS, in Safari, Chrome, Edge, or
Firefox.

Consequence for an in-browser enrollment page that generates a key and
submits a CSR: the flow issues a real, valid certificate whose key
**cannot be presented to an mTLS-protected site** by the browser that
generated it.

## Where TLS-usable keys can actually come from

When server-side key generation and .p12 downloads are ruled out, a key
reaches a TLS-usable store only via:

1. **A local tool that writes into that store** — on macOS/Linux an
   installer script's openssl + keychain/NSS path; on Windows `certreq`
   with the Microsoft Software Key Storage Provider.
2. **An app that owns its own trust** — for example a native (Capacitor
   or similar) app on iOS/Android.

The in-browser path is a genuine third case, but only for consumers
that live inside the browser or app — they hold the key where they can
use it.

## Documentation rule

Never describe an in-browser key-generation flow as "enrolls this browser
for site access over client-certificate auth":

- On macOS/Linux/Windows, point the reader at the local-tool path for
  browser client auth.
- On iOS/Android, state that full browser access rides a native app — and
  do not promise app UI that does not exist.
